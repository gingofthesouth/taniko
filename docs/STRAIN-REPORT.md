# Strain Report — Mapping the Origin iOS Harness onto Schema Set v0.1.0

> Historical record: this report describes schema set v0.1.0 as it stood when first mapped against real code. It is preserved as evidence, not maintained as current guidance — the schemas it discusses have since evolved. Specialised terms are defined in the [glossary](GLOSSARY.md).

This report records the first reality test of the schema set: taking the origin app's existing, production agent harness (`bin/harness` plus its instruction files — roughly 1,160 lines of Swift) and mapping it, feature by feature, onto the v0.1.0 schemas, which had been drafted clean-room from the contracts alone. Every mismatch found was sorted into one of three buckets:

- **Schema gap** — the clean-room schema missed something real; fix the schema.
- **Adapter detail** — iOS-specific behaviour that belongs in the project's own adapter; the schema is unchanged.
- **Conformance shortfall** — the implementation falls short of the contracts; fix the harness, eventually.

The schema changes arising from this report were applied in schema set v0.2.0.

> Note: when this report was moved into the Tāniko repository, references identifying the origin project were replaced with generic equivalents, and the text was rewritten for clarity. The findings themselves are unchanged.

## What mapped cleanly

More than expected. The harness's verification pipeline (lint → build → targeted tests → full tests) matches the declaration's ordered-tiers model exactly, including failing fast in cost order. Its feedback to the agent was already trimmed to character budgets (lint ≤ 2,000 characters, build ≤ 5 × 400, tests ≤ 1,200, final verdict ≤ 2,500) — the bounded-feedback contract, implemented before the schema existed. Independent convergence like this is good evidence the bound belongs in the contract. The harness's `.agent/` directory is the state-directory contract in practice: gitignored, rotated, holding progress, cache, and logs. Its tree hashing is content-based with no time-based expiry anywhere, matching the invalidation rule. The distinction between *error* and *fail* already exists in the code: lint distinguishes "the linter broke" from "the linter found violations," and a test run that produces no parseable result bundle is reported as a tooling failure, not a test failure — exactly the schema's three-verdict semantics (pass / fail / error).

One feature that looked like it might strain the model didn't. The "targeted tests" stage is dynamic — it maps changed files to their tests at runtime — which seemed at odds with a statically declared tier. But the declared command is simply an adapter subcommand (`harness test --changed`), and the dynamism lives behind it. This is worth canonising as the pattern: **tiers point at adapter commands, never raw tools.**

## Schema gaps (fixed in v0.2.0)

1. **Verify results describe a pipeline run, not a single tier.** The biggest find. v0.1.0 modelled one verify-result per tier invocation; the harness produces one verdict per *pipeline run*, summarising all stages — and that verdict is the unit everything else consumes: it is what progress records point at, what gets cached, and what the agent iterates against. The harness is right: "the verify that passed" is the natural thing for evidence references to cite, and per-tier records are internal detail. v0.2.0 rewrote verify-result as a pipeline envelope: an overall verdict, a `stages` array (id, cost class, verdict, duration, counts), the failed stage, and feedback from it.

2. **Cached verdict replay was unrepresentable — and it is the single highest-value mechanism.** Running `verify` on an unchanged tree replays the previous verdict in under a second instead of ~80 seconds, keyed by a SHA-256 hash over HEAD, the tracked diff, and untracked file contents. v0.1.0 had no way to say "this result is a replay." v0.2.0 added a `cache` block (`replayed`, `tree_hash`, `recorded_at`), and the contract gained the principle that makes replay legitimate: determinism is what licenses it — same tree, same verdict, which holds only because a nondeterministic tier is already a contract violation. Structurally, verdict caching is the tool-cache pattern applied to verification itself, but the verdict deserves first-class representation because it *is* evidence, not just a saved observation.

3. **Named profiles.** The harness's `--quick` flag runs a named subset of tiers with its own cache key, so a quick pass can never masquerade as a full pass. v0.2.0 added `verify.profiles` to the declaration (with "full" reserved to mean all tiers), a `profile` field on results, and the rule that only a full-profile pass can satisfy the evidence requirement for marking work done.

4. **Flaky-test disclosure.** The full suite reruns failed tests once and reports any pass-on-retry as `FLAKY-PASS` with the test names — disclosed, never hidden, mirroring CI's own retry behaviour. v0.1.0's contract said flaky tiers are violations "to be fixed or quarantined," which is right as an end state and useless as an operating policy for an 860-test suite. v0.2.0 adopted the harness's pragmatic middle ground as the contract: a *declared* retry policy (`flaky_reruns` per tier, default zero) with *mandatory disclosure* (`flaky_passed` test identifiers in the stage record). Undeclared retries and undisclosed flaky passes remain violations. Note the interaction with gap 2: a flaky test also poisons verdict-cache validity — same tree, different verdict — so retry-and-disclose is also what keeps replay honest.

5. **Doctor checks are broader than toolchain versions.** The origin app's doctor checks seven things, and only two are version checks. The rest are health checks the v0.1.0 shape (tool id / requirement / found version) could not express: simulator availability (resource discovery), derived-data writability (a path check), disk capacity (a threshold with a warning level), presence of a secrets file (conditional, warning only), and whether `xcresulttool` responds. v0.2.0 generalised checks to `{id, kind: tool|resource|path|capacity|file|other, status: pass|warn|fail|error, requirement?, found?}` and added `warn` as a non-halting advisory, both per check and as an overall status (exit 0). The exercise also surfaced a conceptual split the contracts now name: doctor has two duties — **drift detection** (declaration versus actual machine) and **health checking** (is the environment usable right now) — and the origin harness currently does only the second (see the shortfalls section).

6. **Preconditions.** The harness's secrets step runs inside verify but is not a tier: it *provisions* rather than judges — it generates a gitignored file if missing, skips silently on branches without the generator script, and produces no verdict. v0.2.0 added `verify.preconditions` to the declaration: commands that run before the first tier, with an optional file-exists condition, whose failure is always an `error` (environment problem), never a `fail` (code problem).

7. **Learned facts.** The harness's progress file has a `Learned:` section — repository facts worth keeping across sessions ("this test is flaky," "surprising coupling here") — and v0.1.0's progress schema had items and decisions but nowhere to put these. It is a real, distinct category: the raw material of incremental improvement. v0.2.0 added a `learned` array, with the guidance that facts which stabilise should graduate out of gitignored memory into committed instructions (the canonical instructions file or a skill). The origin app's add-source-file skill is exactly that — a graduated learned fact about a known Xcode project-file bug.

**One open tension, deliberately left unresolved:** progress is a markdown file in the origin harness and a JSON document in the schema. Markdown is optimised for the actual reader and writer (the model); JSON is optimised for tooling and validation. The options are for the engine to own JSON and render a markdown view, or for the schema to become an information contract with markdown as an allowed encoding. Recommendation: run more real sessions before deciding — this choice should be settled by observed friction, not taste. Tracked as an open decision, not forced into v0.2.0.

## Adapter details (schema unchanged — confirmed as project-specific territory)

The predicted strain points landed almost exactly where expected. The harness's build-log and test-result parsers confirm the prediction that "xcodebuild output needs a real parser" — roughly 170 lines of the adapter exist purely to distil Apple tooling output into the bounded feedback envelope, and every platform's adapter will have an equivalent. Also confirmed as adapter-side: the changed-file-to-test mapping convention (`Foo.swift` → `FooTests`); simulator auto-selection with its private cache file (the state directory permits adapter-private files, now noted in the schema documentation); a shared derived-data slot that keeps the harness and fastlane on one warm build; a hard-won `-collect-test-diagnostics never` flag that would be destroyed by well-meaning "cleanup" — precisely why decision records matter; the self-rebuilding harness shim; log and result rotation counts; the app's three-target test-membership rule and the known project-file bug (skill territory); and the multi-tool instruction pattern (one canonical instructions file, a symlink for one agent CLI, a pointer file for another) — a pattern worth documenting in this repository's guidance, but not a data schema.

## Conformance shortfalls in the origin harness

Named plainly, because finding them is the point of the exercise — with the caveat that all three are consistent with a deliberately staged rollout (two layers built, the third pending at the time of this report).

**No enforced sandbox; no tamper isolation.** Every boundary was instructional: "don't touch the CI config," "never edit the generated secrets file," "don't weaken a failing test." Nothing *prevented* the agent from editing the verifier itself — the harness sources, the lint configuration, and the test files were all writable, and the self-rebuild shim would faithfully compile a tampered harness. The tree hash makes tampering *visible* (harness edits change the cache key and appear in the diff a human reviews), which is real mitigation — but it is detection, not prevention. This is the largest contract gap, and the cheapest first step requires no new machinery: encode the protected-path list in the agent CLI's own permission layer (deny writes to the harness sources, the lint config, the test directory when the task isn't test-writing, the test plans, and CI files).

**No budget caps.** Nothing bounded verify attempts; the loop was hard-gated but unbounded, with a human as the only backstop against runaway behaviour. This is consistent with being pre-graph — attempt budgets naturally live where retry routing lives — but an interim floor is worth having: a per-tree-lineage attempt counter in the state directory, so the harness itself can say "attempt 7 — consider escalating" even before a graph layer exists to enforce it.

**Doctor checks health, not drift.** There was no committed declaration to drift *from*: the requirements were implicit in code (any Xcode passes if `xcode-select` resolves; the 20 GB disk floor was hardcoded), and doctor ran "after machine changes" by instruction rather than at session start as a halting gate. The declaration schema is precisely the missing piece, and the origin app is its ideal first consumer: a declaration would pin the Xcode version that today is only checked for existence.

## What this exercise could not test

The routing-record schema was untouched by this mapping — the origin app had no graph layer yet — so it remained clean-room and was flagged as the least trustworthy schema in the set until the graph layer landed and the exercise was repeated against it. (It was: see RESOLUTIONS-0.4.0.md.)

## An insight worth keeping

The flagship harness mechanism in the article that inspired this project — a per-file read cache — is the one thing the origin harness *didn't* build. What it built instead (disciplined instructions about token use, plus whole-tree verdict caching) captured most of the value, because the expensive redundant observation in build-and-test work is the 80-second verification run, not the 2,000-token file read — and modern agent CLIs already manage read context tolerably well. The generic repository should therefore present observation caching as an optional optimisation and verdict caching as the load-bearing mechanism — inverting the article's emphasis, on evidence.

## Addendum: the skills

The origin app's four agent skills and its Copilot pointer file were mapped after the initial report. No schema changes resulted — skills are instruction-layer artifacts, not data records — but they resolved several questions the harness code alone left open, and two contract clauses were extended because of them.

**The improvement loop is real and closed.** Each skill is a cluster of stabilised learned facts around one task shape (the project-file bug, a dependency version pin, simulator recovery procedures, test-quarantine mechanics), and the debug-verify-failure skill explicitly instructs the agent to record persistent flaky tests in the progress file's `Learned:` section — the skill layer feeding the memory layer, whose stable facts graduate back into skills. This directly validated v0.2.0's `learned` design and its graduation guidance.

**Bounded feedback requires an escalation path.** The debug-verify-failure skill is the release valve that makes character-budgeted verdicts survivable: when the summary is insufficient, the agent escalates *narrowly* — grepping the retained log, querying the result bundle with specific subcommands — rather than dumping everything into context. This is the documented usage protocol for the verify-result's raw-output references, and the loop contract now states the pairing explicitly: the bound and its escalation path together are the contract.

**Skills classify cleanly by layer,** which is independent validation of the layer model itself: add-source-file is a harness skill (project-structure hazards), write-unit-tests and debug-verify-failure are loop skills (producing and consuming evidence), and the UI-testing skill guards the cost boundary of the most expensive tier. The write-unit-tests skill also demonstrates a pattern now in the contracts: skills defending the conventions that harness mechanisms depend on ("class name = file name — this convention powers targeted testing; keep it").

**Two additional findings.** A shell script that checks UI-test group membership — seconds to run, no build required, deterministic, enforcing a repository invariant — is a static verification tier in everything but name, and was living only in CI; it belongs in the local verify pipeline. And the UI-test quarantine list plus the test plans are the highest-value additions to the protected-paths list: the quarantine file is the single easiest edit by which an agent could make a gate pass without visibly changing build behaviour.

**An instruction-layer pattern worth shipping in the generic repository:** one canonical rules file; per-tool pointer files that redundantly inline the top one or two invariants ("even if you read nothing else…"); and per-adapter skills as the distribution unit for graduated knowledge. This matches the contracts-plus-installer-skill design the repository was already heading toward, and adds a fourth element: adapters ship task skills, not just verify commands.
